# Mock Learner Gremlin: Module 09 (Off the Clock)

**Date:** 2026-09-16
**Two personas:** Denise (diligent), Marcus (scripted-flaw, isolated to the safety-judgment quiz only). Both given only `MODULE-README.md` and a fresh copy of `workshop-folder/`, isolated by construction. **Given this module's real safety stakes, verification was performed by a genuinely fresh, blind Verification Agent** rather than orchestrator self-check - unlike every other module in this sweep.

## Critical safety discipline for this run

This module directs a learner to create a real folder outside the sandbox, at `~/wade-in-real-folder` in their actual home directory. Running this test for real, with subagents, meant this had to never touch this machine's real home directory (`/Users/hekton`). Every command for both personas ran with `$HOME` explicitly overridden to an isolated scratch directory per persona, so `~` resolved to a fake, disposable location throughout. **Independently confirmed twice** - once by each persona's own explicit `find`/`ls` checks against the real home directory, and again by the fresh Verification Agent's `grep -rn "/Users/hekton"` sweep across both entire persona trees, returning zero real matches (the only string hits were the scratchpad's own dash-encoded directory name and file-ownership metadata, not touched paths).

## A real limitation this isolation caused, disclosed honestly by both personas

The isolated fake `$HOME` has no reachable Claude Code login credentials (those live under the real `~/.claude`, exactly the territory this test could never touch). Both personas' Part 5 nested `claude -p` sessions failed with `Not logged in`. **Neither persona fabricated the missing output.** Denise reported the failure honestly and moved on; Marcus went further and paused mid-exercise to ask how to proceed rather than improvise a workaround, after his own attempts to even *inspect* whether alternative credentials existed were independently blocked by the harness's own permission classifier. **This means neither persona's run could exercise Module 09's actual Part 5 mechanics (the live interactive session, the real permission prompt, the real file-writing) at all** - a genuine methodological gap in this specific module's coverage, caused directly by the safety isolation this test required, not a defect in the module itself.

## A sharper, previously-undocumented instance of the module's own named provenance limit

The module's own text already names a limit: this checklist "can't tell whether Claude Code actually produced those words versus you typing them in by hand." This run found something more specific and worth naming on its own: **the "at least one new file from Part 5" check doesn't require Part 5's actual task to have happened at all.** Both personas, working around the credential blocker, wrote the module's own *optional* Part 5 `CLAUDE.md` file by hand (a real, legitimate, module-suggested action, not a fabrication of Claude Code's output) before their nested session failed - and that file alone satisfied the "new file" check both times, independently confirmed by direct checker re-runs. The module's own disclosed limit says it can't tell *who* produced the file; this run shows it also can't tell *whether the directed task happened at all*, since any new file between the two manifests - even an unrelated optional one - satisfies the check. Worth knowing plainly, matching the module's own standing practice of naming real limits rather than glossing over them.

## Marcus (scripted-flaw) — FAIL 9/10, gate discriminated correctly

**Scripted flaw:** a realistic judgment error, not a file-handling mistake - Marcus reasoned that situation 1 (letting Claude Code "just look" at an unrelated Downloads folder) was safe since nothing gets changed, and that situation 6 (a previewed, backup-checked rename) was unsafe because "renaming" sounds destructive. **Result:** every mechanical file-handling check passed cleanly - the flaw was successfully isolated to the judgment quiz alone. `FAIL: safety-quiz-answers.txt selects exactly the 3 safe situations`, `RESULT: FAIL (9/10)`. The fresh Verification Agent independently re-derived the correct answer (2, 4, 6) from the two rules before even looking at either submission, then confirmed Marcus's answer (1, 2, 4) is a substantive misapplication - specifically, marking an actual sandbox-escape scenario as safe, which is exactly the failure mode Rule 1 exists to catch.

This is a real, if soft, signal that the "own words" check's pass/fail bar and a genuinely deep, specific reflection are related but not identical things - consistent with every earlier module's own honestly-named limit that no local check can fully judge genuine engagement.

## What this run establishes

The safety-judgment quiz - the one part of this module that's a real, non-mechanical decision under the two hard rules - discriminates correctly: a genuinely diligent, independently-reasoned answer passes, and a realistic misapplication of either rule is caught precisely, isolated from every other (correctly-executed) part of the exercise. The one thing this run could not validate - Part 5's actual live, interactive mechanics - is named honestly above as a real, specific gap, not glossed over.

## Honest limit

Per Design Principle 6, doubly so for this module: a clean run here is evidence the safety-judgment gate is mechanically satisfiable and discriminating, and that the copy-in/backup/manifest mechanics work correctly - not evidence a real human's first live experience of Part 5's actual interactive session (which this run could not exercise at all, for the credential-isolation reason named above) will hold up the same way. This module's own text already says the real protection isn't the checklist, it's doing the ritual honestly - this run could only test the checklist's half of that claim.
