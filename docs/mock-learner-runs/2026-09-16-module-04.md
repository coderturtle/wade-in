# Mock Learner Gremlin: Module 04 (Let It Run)

**Date:** 2026-09-16
**Two personas:** Denise (diligent), Marcus (scripted-flaw). Both given only `MODULE-README.md` and a fresh copy of `workshop-folder/`, isolated by construction. Verification performed directly by the orchestrator (re-running the checker, confirming file contents), not a separate blind agent - see Module 03's report for why.

## A real, concrete documentation bug found by running this for real

The module's own text states *"It prints `RESULT: PASS (7/7)` when everything's there."* Both personas' real, independent runs of the actual checker printed `RESULT: PASS (8/8)` (Denise) and `RESULT: FAIL (5/8)` (Marcus) - both showing 8 total checks, not 7, with identical check descriptions across both runs. Tracing the mismatch: the README's own prose narrates 7 things the checklist checks (real folder, report exists, fixtures unmodified, total right, busiest right, slowest right, answers file) - but the real checker has an 8th check, **"04-scripts/ contains the script itself, not just the report,"** never mentioned anywhere in the module's prose. This is a genuine drift between the checker and its own documentation, not a hypothetical - confirmed by two independent live runs of the real script, not just a static read of the code.

## A second, related finding: script-execution permission is a distinct grant from file-edit permission

Both personas independently discovered the same real Claude Code behavior: `--permission-mode acceptEdits` authorizes file writes but **not** running a script via Bash - a nested session that wrote `door-report.py` under `acceptEdits` alone stalled waiting for approval to actually execute it. Both personas worked around this the same way, independently: scoping `--allowedTools="Bash(python3 *)"` rather than a blanket bypass. This is a real, useful methodology finding for the rest of this sweep (every module past this point that has Claude Code run a script needs the same scoped-Bash-allowlist treatment, not just `acceptEdits`) - and, read the other way, it's a small piece of positive evidence about the real product's own permission granularity: write access genuinely doesn't imply execute access, matching good security practice.

## Denise (diligent) — PASS 8/8, independently reconfirmed

Real nested `claude -p` calls for the plan (Part 2) and the write-and-run (Part 3), the second requiring the scoped-Bash-allowlist workaround above. The plan step is worth noting on its own: rather than guessing, the nested session asked clarifying questions about file naming and confirmed the save location before proceeding - a genuinely good "plan" response, distinct from Marcus's flawed run below where the same plan step accepted a wrong file range without question. Denise's own hand-verification went beyond the module's minimum ask: she summed all 12 raw counts herself (154+132+...+79 = 1709) *before* seeing the script's output, not just spot-checking one night - a stronger independent check than the module requires, and she said so in her own `WHAT_NEXT_TIME` answer. Script and report both landed inside `04-scripts/` this run - orchestrator re-ran the checker directly and reconfirmed `RESULT: PASS (8/8)`.

## Marcus (scripted-flaw) — FAIL 5/8, independently reconfirmed, gate discriminated correctly

**Scripted flaw:** a literal, concrete mistake baked into his own request (not an omission hoping the model would misbehave, per the Module 03 lesson) - Marcus skimmed the fixtures folder quickly and asked Claude Code to read only `door-count-2026-08-01.txt` through `...-08-10.txt`, missing the real 11th and 12th files, and never noticed since his own hand-check (the busiest night, 08-08) happened to still be correct within his truncated range.

**What happened:** the real nested Claude Code invocation did exactly what was asked - produced an internally consistent but factually wrong report (total off by 163, the missing 79-count night on the 12th meaning the wrong night got reported as slowest). The checker caught both: `FAIL: door-report.txt has the exact monthly total (expected 1709, found '1546')` and `FAIL: door-report.txt has the exact worst night (expected 2026-08-12 / 79, found '2026-08-06' / '88')`. Also failed the (undocumented) 8th check, since this run's script landed outside `04-scripts/` rather than inside it - a separate issue from the scripted flaw itself (see below).

Marcus's own hand-check (Part 4) did not catch the error, honestly - the module only asks the learner to verify the *named busiest night*, and his flawed range's busiest night happened to still be genuinely correct (08-08 really is the busiest night even across all 12 files). This is a real, structural observation about Part 4's verification design: checking only the one night named as busiest can't catch an error in which nights were included at all, only whether the arithmetic on the included nights is right. `answers.txt` was judged genuine - Marcus's `WHAT_NEXT_TIME` answer reflects a real, specific process observation (split plan/run calls losing continuity) rather than foreknowledge of the file-count mistake he didn't know he'd made.

## What varies between the two runs, not systematically

The 8th check ("script itself present in `04-scripts/`") passed for Denise and failed for Marcus - but this tracks the two personas' different literal prompts and how the nested Claude Code session happened to organize its own output that run, not a fixed module defect. Denise's diligent, careful attempt did land the script in the right place. This is worth knowing (a careless or ambiguous request risks the script landing outside `04-scripts/`, independent of whether the actual math is right) but isn't itself evidence the module's exercise design is broken - just another reason the module's own suggested prompt could be tightened to say explicitly where the script itself should live, not just the report.

## What this run establishes

The gate discriminates correctly: a genuinely diligent, well-verified attempt (including a stronger-than-required independent hand-check) passes; a realistic, literal file-range mistake produces a genuinely wrong report that the checker catches on two independent counts. Both personas' scripts were real, running Python against real fixture files, not fabricated. One real documentation bug found (7/7 vs. the actual 8/8) and one real, useful product-behavior finding (write permission ≠ execute permission) - both concrete, not hypothetical, since both surfaced from two independent live runs agreeing with each other.
