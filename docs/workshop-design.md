Full critique at `wade-in-private/docs/codex-critique-workshop-design-2026-09-14.md`. The naming pass is complete and settled (see §5). Repo facts: classification `factory-output`, privacy boundary public, owner coderturtle, GitHub `coderturtle/wade-in`, private sibling `wade-in-private` (already scaffolded). Deployment/DNS is deliberately a later-phase concern once real content exists, noted once here, not planned in this document. **This reconciliation pass fixed every CONFIRMED comparative/factual error Codex found and tightened several checker specs it showed didn't verify what they claimed; it did not resolve every open design question Codex surfaced (Tier-2's completion contract, the platform decision, the CLAUDE.md file-identity ambiguity) — those are named explicitly below as still-open, not silently carried forward as solved.**

## 1. The one-line problem

Claude Code is a genuinely capable general-purpose work tool that most non-technical knowledge workers will never open, because it lives behind a surface — the terminal — that they have never once used and that most existing tutorials assume they have. (Both the comparative "most capable" claim and the "every tutorial" claim are this document's own unverified impressions, not a checked survey — see §9's honest disclosure of the same limit, which this line should be read alongside rather than as an exception to.) This workshop's bet: a learner who has literally never opened a terminal can, through one gated, continuously-scenarioed arc, become someone who launches Claude Code themselves and does real research, document, spreadsheet-adjacent, and light-automation work with it — gated by a genuinely deterministic checker script at every module, which no prior non-engineering workshop in this factory could offer (§8).

## 2. Audience

Non-technical knowledge workers — the same audience shape as `copilot-fluent` (no git, no CLI, no coding-agent background), but with an explicitly **harder floor: zero prior terminal experience**. The design assumption is a learner who has never opened a terminal, does not know what a prompt or cursor is, and has never typed `cd` or `ls`. This matters structurally, not just tonally: `copilot-fluent`'s learner worked inside M365 apps they already trusted and used daily; this workshop has no equivalent already-trusted surface, because Claude Code's own interface *is* the subject. Module 01 exists specifically to build the floor the rest of the arc stands on (§7) — no prior workshop in this factory has had to teach the underlying interface itself before the subject could start.

Hard prerequisites, named plainly rather than discovered mid-module:

- A computer the learner controls (can install software on). **Correction (Codex critique, finding 12): this is not a settled cross-platform commitment.** §11 leaves the platform decision genuinely open, and the module arc as designed (§7) already standardizes on a Unix-shaped checker contract (`check.sh`, `command -v`, `cp`, slash paths) — that is not a platform-neutral design as written. The honest prerequisite for this draft is "a Mac or Linux machine, with Windows support an explicitly open content-time decision," not "macOS, Windows, or Linux" stated as if already resolved.
- An Anthropic account with paid Claude Code access (a Claude subscription that includes Claude Code, or API billing) — **flagged for live verification, not yet confirmed against Anthropic's current published access model** (§11).
- Willingness to install one developer-adjacent tool with hand-held, copy-paste instructions, **and to complete whatever authentication/login step Claude Code currently requires — not yet designed into Module 01, see §11's named gap.** Nothing else is assumed.

**Solo by design — a genuine simplification over `copilot-fluent`, worth naming:** no exercise in this arc requires a second person, a shared tenant, a colleague to share with, or an admin's approval. Every module runs on the learner's own machine. **Correction (Codex critique, finding 13):** not every module runs purely against workshop-provided fictional fixtures — Module 05's sources are real, live, public vendor pages (§7, §9), and Module 09 deliberately leaves the sandbox to touch a few of the learner's own real files (or stand-ins, §7 row 09). The accurate claim: every module's *starting business data* (client records, booking sheets, financial figures) is fictional and workshop-supplied; Modules 05 and 09 are named, deliberate exceptions that reach outside that fictional data (public web sources; the learner's own optional real files) respectively. The only per-learner variance beyond that is their own machine and account (§11), not an organization's policy surface.

## 3. Format

Self-paced, public — the published site is the **primary learner surface**, same as `copilot-fluent`, not a maintainer build journal (a no-git audience reads modules on the website, not the repo). Site implementation is a later-phase deliverable, not this document's.

**A real structural difference from `copilot-fluent`, stated explicitly rather than inherited:** `copilot-fluent` had a two-way split — the site is where you read, your M365 apps are where you do. This workshop has a **three-way split**: the **site** carries the instructions, the scenario, and each module's gate; the **terminal** is where the doing happens; and **Claude Code's own file output** — the files the learner's session actually produces on disk — is the artifact submitted against the gate. The gate is closed by running a checker script against those real files (§8). **Correction (Codex critique, finding 2):** this is *not* the first workshop in this factory to grade a filesystem-resident artifact — `borrow-native` already gates every module on `cargo test`/`cargo clippy` against the learner's real Rust files, and `closed-book`/`heartbeat` use real local artifacts and checker scripts too. The genuinely new thing here is narrower: the first *non-engineering-audience* workshop with a shipped local checker, and the first workshop where "the terminal" and "the filesystem the checker inspects" are the same session a total beginner is driving for the first time. §3's own three-way split (site / terminal / file-output) already names the terminal and the file output as distinct surfaces — treat them as such, not as "the same surface," which was an internal inconsistency in the prior draft.

**Distribution, given a no-git audience:** the workshop materials (fixtures, the sandboxed scratch directory, the checker scripts) ship as a downloadable archive from the site — the learner never clones anything. Exact packaging is a content-time decision; the design constraint it must satisfy is "obtainable and unpackable by someone who has never used a terminal, before Module 01 has taught them anything."

**Adopted, not silently omitted: the site-publishes-module-content vocabulary-leak safeguard `copilot-fluent` had to build.** Per the Workshop Gremlin's non-engineering variant, a site that renders `modules/*/README.md` directly must render a plain, vocabulary-free placeholder for any module still carrying its "Skeleton only" banner (the module-README template's own vocabulary — "Tier 1," "Coachgremlin," "self-attested," "grading key" — is maintainer-facing and unsafe to publish raw). This workshop's site inherits that exact safeguard as a build requirement, not a thing to rediscover at content time.

**Rough total time commitment, stated for a busy-professional audience:** budget roughly 10-13 hours across ten modules, unevenly distributed — Module 01 is deliberately slow (45-60 minutes for material an engineer would skim in five), and the Module 10 capstone is clearly the longest single sitting (2-3 hours). Named explicitly as an estimate, not a commitment: no module has authored content yet, so this is a judgment call, re-checkable once real content exists — the same hedge `copilot-fluent`'s §3 carries.

## 4. Subject vs. method

Named separately per the Workshop Gremlin's standing discipline, and with an unusual wrinkle this factory has seen only once before (`terminal-velocity`): subject and method partially collapse into each other here. The interface being taught is also the interface the learning happens in.

**Subject:** Claude Code — the real `claude` CLI in a real terminal, no wrapper, no simplified or hidden version. The gentleness this audience needs comes from pacing and hand-holding in the content, never from hiding the real tool — a learner who finishes this workshop has been using the actual product from Module 02 onward, so nothing is left to "graduate to." In-scope capabilities, enumerated as the closed set the module arc must cover (§7 carries the coverage check):

1. File reading and editing (Claude Code reads and edits files at the learner's direction).
2. Running commands — including simple scripts Claude Code writes and runs on the learner's behalf; the learner directs and verifies, never reads or writes code by hand.
3. Web research (Claude Code's web search/fetch capabilities).
4. File-based automation and templating — batch renaming, CSV/spreadsheet-adjacent munging, templated document generation.

Plus two things this workshop owns that aren't Claude Code capabilities at all: **terminal literacy itself** (Module 01, before Claude Code enters the picture) and **the safety discipline for pointing a real agent at real files** (Module 09, taught late-arc as an explicit skill, never assumed — see §12).

**Explicitly out of scope, with the line that matters named:** git, subagents/Task delegation, MCP servers — and, most importantly, **any exercise where the learner is expected to read or write code themselves** rather than directing Claude Code to do so. The moment a module asks the learner to understand a script's contents, it has quietly become a programming workshop, which this is not. Learners direct, constrain, and verify; Claude Code implements. This document treats that line as a hard design rule for every module in §7, and flags it here as a line that is easy to drift across accidentally at content time (a checker verifying a script's *output* is fine; a rubric asking the learner to *explain the script* is a violation).

**Method:** a named-scenario-driven, two-tier-gated, self-paced format. **Correction (Codex critique, finding 5):** this is the broad hands-on, self-paced lineage every prior workshop shares — it is not true that all three specific properties (named-scenario, two-tier, self-paced) were universal from the start: `terminal-velocity` ran an all-subjective rubric with no deterministic tier, and the named-shared-project pattern was established later by `borrow-native` and was initially missed even by `heartbeat`. This workshop's distinguishing property is narrower and real: its Tier 1 is a genuinely scriptable, deterministic checker (§8), closer to `borrow-native`'s `cargo test` tier than to `copilot-fluent`'s required-output checklist — the first time this factory's non-engineering-audience variant has had one.

## 5. The shared scenario: The Double Deuce

**The Double Deuce** is a live-music venue and events hall in the fictional small town of Jasper, Missouri. The learner plays its newly hired **Operations Coordinator** — a deliberately cross-functional role (vendor research, event documents, booking spreadsheets, file wrangling, light automation). **Correction (Codex critique, finding 4):** the prior draft contrasted this with "one department's narrow work the way `copilot-fluent`'s financial-advisory firm was" — `copilot-fluent` never actually assigns its learner a narrow departmental role; its own arc spans prompts, conversation management, Word/Outlook, Excel/PowerPoint, Teams, and agent creation. The honest comparison is simpler: this workshop's role is cross-functional by explicit design, same as `copilot-fluent`'s was, not a departure from it. Every module's exercise is drawn from this one continuing workplace, per the factory's named-shared-project principle (`relay`, `Checkout`, Kellerman & Castle).

**The scenario device that generates the fixtures:** the learner's predecessor — a long-serving, recently retired operations man named **W. Garrett** — left behind years of chaotic files: inconsistently named photos, half-corrected phone lists, unreconciled booking sheets, and a handwritten-feeling operations handbook. Inheriting and gradually taming Garrett's files *is* the arc's continuing thread, and the learner's own growing `my-pack/` (§7, Module 10) is framed in-scenario as writing the handbook's replacement.

**Naming, recorded as settled decisions, not proposals:**

- **The workshop name, Wade In, is settled** — chosen by the human from 8 candidates during the naming pass, not re-litigated here. Rationale: it plays two ways at once. To the learner it is the literal promise — ease in gently, ankle-deep first, a workshop for wading rather than diving. Inside the factory's established Patrick-Swayze-movie-universe in-joke pattern, it is a *Road House* callback: Wade Garrett, the veteran mentor. Same discipline as Kellerman & Castle: the reference plays completely straight during all graded content and is revealed once, deliberately, after the capstone.
- **The org and cast are this document's own decision**, made here the way `copilot-fluent`'s §5 made its firm a real decision: the Double Deuce is the *Road House* venue itself (Jasper, Missouri is the film's setting), and the predecessor whose files the learner inherits is Wade Garrett — which is also why the workshop is named what it is, a fact the learner only learns at the reveal. The cast is drawn from the same Swayze-verse but deliberately does **not** reuse Kellerman & Castle's cast (Johnny Castle, Baby Houseman, Sam Wheat, Molly Jensen, Dalton, Bodhi, Oda Mae Brown, and K&C's own Wade Garrett stay at K&C; the two workshops share a universe, not a payroll — the one name that appears in both, Garrett, is here only as the offscreen predecessor, a wink the reveal can enjoy rather than a continuity claim). No gate ever keys on a character's identity, same as `copilot-fluent`.

**Scenario guardrails** (lighter than `copilot-fluent`'s financial-liability set, because the actual risk profile is different — see §12 for where this workshop's real first-class safety layer lives instead):

1. All *supplied business* fixture data (client records, bookings, financial figures) is plainly fictional — no real vendors as scenario characters, no realistic personal data, no real addresses or account numbers. This does not apply to Module 05's real public vendor research targets or Module 09's optional real personal files, both named exceptions per §2.

## 6. Curriculum anchor: none external — and why that's stated rather than papered over

**There is no external certification anchor for this workshop, on purpose.** Unlike AB-730 for `copilot-fluent` or Ardan Labs for `borrow-native`, no known real, current, published certification or blueprint exists for "using an agentic coding CLI as a non-engineer." This document does not invent one, imply equivalence to one, or stretch an adjacent one to fit. **Standing rule, borrowed from `copilot-fluent`'s own hard-won §6 discipline:** if a future pass is tempted to name an external credential this workshop "maps to," that temptation is the signal to verify live that such a credential exists and actually fits — not to trust the temptation.

**Internal awareness note, not a learner-facing claim:** Anthropic's own Claude Certification program — specifically the **Claude Certified Architect** track (Foundations then Professional level) that this factory's `closed-book` workshop anchors to — exists, is real, and its audience (`closed-book`'s own) is agent-literate practitioners already comfortable driving Claude Code daily. **Correction (Codex critique, finding 6):** calling this "the engineer-track program" overstates precision `closed-book`'s own docs don't establish; the accurate description is "an agent-literate-practitioner audience," and the human's own characterization of it as "more engineer focused" (relative to Wade In's zero-terminal-experience audience) is the operative distinction, not a formal track label. Where mechanics genuinely overlap (how to write an effective prompt; how to verify AI output), `closed-book`'s already-authored content and structure may be reusable raw material at content time. That is a maintainer-side reuse note only; no learner-facing copy may present Claude Certification as this workshop's target, stepping stone, or equivalent.

**Success is therefore defined entirely internally**, by this workshop's own module arc and gate design: a learner who has passed every gate can open a terminal, launch Claude Code, and do real research/document/spreadsheet-adjacent/automation work. **Correction (Codex critique, finding 17):** the capstone itself (Module 10) is sandboxed and uses a supplied fixture packet, not the learner's real files — and Module 09's real-folder exercise permits stand-ins, so a completer may never have touched personal files at all. The accurate claim is narrower: the arc evidences the *skills* transfer to real files (Module 09 teaches and checker-verifies the ritual for doing so safely), not that every completer has demonstrably done real-file work by the end — carried forward by the takeaway pack (§7), which is what actually travels with the learner afterward. The honesty cost of having no external anchor is named plainly: there is no third-party bar to dogfood against, so this workshop's validation burden falls entirely on §10's mechanisms (adversarial dry runs, Mock Learner Gremlin passes, and a real-human pilot), and its coverage claims (§7) are self-referential — checked by enumeration against §4's own in-scope list, which this document controls. That is a weaker external position than `copilot-fluent` had, stated as such rather than compensated for with an invented anchor.

## 7. The module arc

**Arc shape:** nine modules plus a synthesis capstone (ten total), inside this factory's established sizes. The sequencing logic is a dependency ramp, not a strict linear one, and **the prior draft overstated how clean it is (Codex critique, finding 9), corrected here:** Module 01 already requires running `check.sh 01`, so it is not accurate that "nothing runs scripts" before 03→04 — the correct claim is nothing runs a *Claude-authored* script before Module 04, since Module 01's checker is workshop-provided and run directly by the learner, not generated by Claude Code. Module 01 also introduces the `claude` CLI install and a `command -v` probe, so "Claude Code does not appear until 02" is also inaccurate as written — Module 01 installs it; Module 02 is the first module where the learner actually *uses* it in a session, which is the claim that should have been made. And it is not true that Modules 05-08 each add exactly one new capability on a stable base: Module 06 largely re-exercises the file/document work Module 03 already introduced (applied to a new artifact shape), and Modules 07-08 both exercise automation/templating rather than each introducing something distinct. The real sequencing claim, checked against the table's own Prerequisites column (02→01, 03→02, 04→03, 05→02, 06→03, 07→04, 08→04/07, 09→03/04, 10→01-09): the prerequisite graph is acyclic and every module's prerequisite is strictly earlier — that part of the original claim holds.

**Coverage check by direct enumeration** (per §4's closed in-scope list, counted rather than assumed): capability 1, file read/edit — directly exercised and checker-gated in Modules 03 and 06. Capability 2, running commands/Claude-authored scripts — directly exercised and checker-gated in Modules 04 and 08. Capability 3, web research — directly exercised in Module 05 (with the arc's weakest deterministic tier, named in its row and in §8, not hidden). Capability 4, automation/templating (including CSV munging) — directly exercised and checker-gated in Modules 07 and 08. That is 4/4 in-scope capabilities each **assigned** to at least one checker-gated module. **Qualification (Codex critique, finding 10):** "directly exercised" needs the same designed-path qualifier `copilot-fluent` §7 explicitly supplied — Module 05's checker is `[structural-only]` (§7 row 05, §8), meaning it verifies the brief's shape and sourcing discipline but cannot establish that web research actually happened or that any claim is true, and its stated fallback substitutes cached excerpts for live web access. So this 4/4 count means "assigned to an honest learner's designed-path attempt," not "mechanically evidenced for every completer" — the stronger reading would be false. This count is also this document's own enumeration against its own list — flagged per §6 as self-referential.

**Mechanical-checkability discipline, applied to every Tier-1 item below and tightened beyond `copilot-fluent`'s version using this factory's own subsequent evidence:** every Tier-1 item is a count, a checker-recomputed value, an exact string *the module gave the learner up front*, or a closed-set comparison. Three sub-rules, each traceable to a specific prior finding:

- **No natural-language exact-phrase checks, ever.** Mock Learner Gremlin's Module 07 re-run (`copilot-fluent`, 2026-09-14) proved a fully correct, fully diligent submission can match 0 of 5 required phrases purely through normal wording variation. Every exact string a Wade In checker looks for is either (a) recomputed by the checker from pristine fixtures (a total, a count, a date), (b) explicitly specified to the learner in the module text ("name the file exactly `bookings-clean.csv`"; "the header row must be exactly `id,name,event_date,deposit,balance,total_due`"), or (c) a closed-set membership/absence check. Never a phrase the learner must happen to word right.
- **Checker-recomputed ground truth beats embedded answer keys wherever the task allows.** A checker that re-derives the expected total from the fixture files is testing the work, not the learner's ability to transcribe a key — and it stays correct if fixtures are revised.
- **`[structural-only]` tags mark honesty, not failure.** Where a task's correctness is genuinely not machine-checkable (does a research brief's claim match its cited source), the Tier-1 item checks structure only and says so; the substance moves to Tier 2 explicitly rather than being dressed up as a mechanical check.

## 8. The two-tier gate

**Tier 1 — a real deterministic checker script, this workshop's structural advantage, claimed precisely.** Unlike `copilot-fluent`'s subject (a closed SaaS product whose outputs live inside apps this factory's tooling can't touch), Claude Code's own working medium is the learner's real filesystem — which means a shipped shell script can run REAL, scriptable, deterministic checks against the learner's actual produced files: recomputed totals, checksum comparisons, closed-set membership, exact specified strings. **Correction (Codex critique, finding 1):** the accurate contrast with `copilot-fluent` is not "real check versus self-attestation" — `copilot-fluent`'s own Tier 1 was genuinely mechanically checkable too (counts, exact-string comparisons against a hidden key, closed-set answers), just without a *product-native correctness oracle* to check against, and self-attestation was one explicitly-tagged subset of its items, not the whole tier. The real, narrower distinction: this workshop's checker is **locally executable** by the learner's own harness, so it can be run, iterated against, and re-verified before submission — `copilot-fluent`'s checklist required a hidden-key grader because nothing on the learner's own machine could evaluate it. This is genuinely closer to `borrow-native`'s `cargo test` tier (Design Principle 2's "deterministic tier first if one exists") than to `copilot-fluent`'s checklist-plus-hidden-key — the first non-engineering-audience workshop in this factory able to say so. The learner runs the checker either directly (Module 01 taught them how) or by asking Claude Code to run it; either way the only passing signal is the checker's own printed `RESULT: PASS (n/n)` line with the full pass count.

**The known trap, named from this factory's own memory rather than rediscovered — status corrected (Codex critique, finding 7):** `closed-book`'s multi-cycle checker-hardening history produced three real bypass patterns. The Workshop Gremlin's own Follow-Up Actions correctly names all three but marks the item unchecked, calling them "worth promoting into standing guidance" and explicitly "not written up in full" — they are real, documented findings living in this factory's memory system, not yet-promoted standing guidance in the Gremlin's own authoritative file. Wade In treats them as load-bearing anyway, on the theory that a real prior finding doesn't need to be formally promoted before a new checker-building workshop benefits from it — but the accurate status is "informally documented, not yet a standing rule," not "recorded... as guidance any future checker-building workshop must start from." The three: a **checker-execution bypass** (cwd-swap and exit-code tricks defeating a naive checker's assumptions about where it runs and how success is read), a **test-fixture confound** (correlated inputs masking what a check actually inspects), and a prose-checker negation-exclusion bypass. Wade In's checkers are therefore built hardened **from the start, not retrofitted**: each check resolves the workshop root from its own script path (never trusting `cwd`); copies artifacts and pristine fixtures into a fresh neutral temp dir before evaluating; verifies fixture integrity by embedded checksum (so an agent that "fixes" the inputs to match a wrong output fails, not passes); recomputes ground truth from those pristine copies; and prints an explicit pass-count-verified result line with nonzero exit on any failure — so a truncated, errored, or partially-run check can never read as success. The prose-checker bypass is mostly avoided rather than defended: §7's design rule bans natural-language phrase checks outright. A learner's agent could stumble into the cwd/exit-code pattern *by accident, with no intent to game* — that is precisely why this is built in from day one rather than treated as an adversarial edge case.

**A named limit `copilot-fluent` never had to face, stated rather than hidden: the checker ships to the learner.** These are local scripts inside the downloaded workshop folder — inspectable by a curious learner, and more realistically by the learner's own Claude Code session if asked (or if it wanders). A check whose expected values are recomputed from fixtures forces real work regardless (satisfying it *is* doing the task), which is why §7 prefers recomputation everywhere possible; but closed-set keys (Module 09's safety-exercise answers) are readable by anyone who opens the script. The workshop's mitigations are honest but soft: a `CLAUDE.md` instructs sessions never to read or modify `checks/`, and the site tells learners the checker is the referee, not the study guide — and this document names plainly, per the Mock Learner Gremlin's own Design Principle 1, that **an instruction is not a control**. **Open design question, not yet resolved (Codex critique, finding 18):** is this the *same* file as Module 03's learner-editable `wade-in-workshop/CLAUDE.md` (§7 row 03) — in which case the learner (and any session they direct) can edit the very file stating the safety boundary, since Module 03's own checker only requires 3 of 4 headers present, not preservation of specific safety clauses — or a *separate*, non-learner-editable file at a different path? This document does not yet specify, and it should before content time: same-file is simpler to ship but weaker as a control; separate-file is a real design commitment this document hasn't made. Also note plainly: the live repo has no checker, no modules, no site, and no `CLAUDE.md` of either kind yet — every present-tense statement in this section describes an intended mitigation, not a built one. Tier 1 here establishes that the artifact has the required properties; it cannot establish provenance (that Claude Code, directed by this learner, produced it) and cannot stop a determined self-cheater. Both limits are inherent to self-paced local grading and are carried as named limits, not solved problems.

**Tier 2 — an AI-graded conceptual rubric, with a real but partial structural difference from `copilot-fluent`'s controversial Tier 2 — stated honestly rather than oversold (Codex critique, finding 16).** `copilot-fluent`'s Tier 2 had the product being taught grade its own output — a named, untested circularity, criticized specifically for using "the same probabilistic product," with no pinned model, no repeatability guarantee, and no disagreement path. Here the conceptual tier follows every *prior* workshop's shape instead: **Coachgremlin grades it** — Coachgremlin authors and validates the per-module grading prompts, and grading is a separate, fresh-context invocation against the learner's artifact plus a supplied rubric, not the closed product judging work it produced inside itself. Claude Code isn't the closed product being taught the way M365 Copilot was: it's an open harness, and the grading prompt is portable (a learner could in principle run it through any capable model). **But this document does not actually answer `copilot-fluent`'s three specific criticisms** — no model is pinned here either, no repeatability guarantee is stated, and no disagreement path is defined (§7's new named gap, above, covers the missing completion contract this same weakness produces). And by this section's own admission, a self-paced learner's fresh-context grader will, in practice, usually still be a Claude model — fresh context and a portable rubric reduce coupling to the exact product-under-test, they do not eliminate same-model-family circularity. What genuinely differs from `copilot-fluent`: Tier 2 is never the sole arbiter of mechanical correctness here, because Tier 1 genuinely is deterministic — that's a real, narrower advantage, not the full escape from the circularity this section originally claimed. An AI grading AI-assisted work also remains an instance of the over-reliance this workshop teaches learners to watch for — Modules 02 and 09 should name that parallel in content, the same turn-liability-into-teaching move `copilot-fluent` §8 planned. And per the Mock Learner Gremlin's Design Principle 9 (its Module 08 finding), a clean AI self-check is weak evidence against **value-judgment-shaped** failures specifically — Wade In's Tier-2 rubrics are mostly judgment-shaped by construction (that's what Tier 1 left them), so content-time validation must include independent-verification passes, not self-check-only runs. Grading-prompt injection (an artifact hijacking the rubric that reads it) is a smaller surface here than `copilot-fluent`'s injection-teaching module, but the delimiter-and-treat-as-data discipline is carried forward as a content-time acceptance criterion anyway.

## 9. Differentiator vs. existing material

**Verification status, stated first and honestly: unlike `copilot-fluent`'s §9, this section's survey of existing material was NOT verified live during this drafting pass.** The categories below are asserted from general knowledge; a live survey of what "Claude Code for non-engineers" material exists as of this date is deliberately left as a named task for the adversarial-review pass and content time — this document would rather flag the gap than assert a falsifiable "nothing like this exists" claim, which is exactly the kind of claim `copilot-fluent`'s own chain caught itself getting wrong about Microsoft's material.

Against the categories that are safe to name:

- **Anthropic's official Claude Code documentation and quickstarts** are real, good, and assume a reader who already lives in a terminal — install instructions that presume comfort with package managers, examples that presume codebases. They are reference material, not a gated curriculum, and they do not teach the terminal itself. This workshop stands alongside them (they remain the product's source of truth) and below them (starting a full floor earlier).
- **Terminal-literacy primers for beginners** exist in quantity, but teach the terminal as an end or as a programming on-ramp — none known to this draft teach it as a two-hour ramp into agentic non-programming work, and none carry a gate.
- **The general "AI for knowledge workers" genre.** **Correction (Codex critique, finding 3):** it is not accurate to say `copilot-fluent`'s own subject area "teaches chat surfaces without file access" — M365 Copilot requires file-grounding access as a hard prerequisite and Module 06 has learners trace deck figures back to a source spreadsheet. The real, accurate distinction is **arbitrary local filesystem/shell access versus application- and tenant-mediated file grounding**: `copilot-fluent`'s learner works with files *through* Word/Excel/PowerPoint, inside whatever a tenant admin has exposed; this workshop's learner works on files directly, through a shell, with no application or tenant boundary in between. That's a real difference in kind, just not the "no file access at all" contrast the prior draft claimed.

What differentiates this workshop, each claim qualified: **gated, deterministically** — not merely hands-on, and with a stronger gate tier than any prior non-engineering material this factory knows of, including its own (`copilot-fluent`'s checklist tier, per §8); **a genuinely zero-floor on-ramp** that owns terminal literacy rather than outsourcing it; **one continuing scenario** with a keepable, personal takeaway pack; **a taught safety discipline** for real-file work (§12) that ad-hoc tutorials skip. Each of these is a design claim about an unbuilt workshop, not an evidenced advantage — per §10, none graduates past "designed to" until validated.

## 10. External validation / dogfooding

With no external certification to sit (§6), this workshop's validation is built from three mechanisms, each a stated commitment rather than existing evidence:

1. **Adversarial checker dry runs, from the first checker built.** Every module's checker gets a `borrow-native`-style good/naive pair before the module ships: a correct attempt must pass with the full count, and at least one scripted-flaw attempt (author-constructed with one concrete mistake, per the Mock Learner Gremlin's hard-won finding that personality briefs don't produce failures) must fail — plus the §8 bypass patterns (cwd-swap, doctored fixture, partial run) each demonstrated to fail loudly.
2. **Mock Learner Gremlin per module** (per Coachgremlin's Workflow step 8), with personas rebuilt for this audience — a genuinely zero-terminal-experience persona, not `copilot-fluent`'s office-worker persona reused. **A hypothesized fidelity advantage, not yet a proven one (Codex critique, flagged-for-verification 7):** because this subject's surface is itself scriptable, a mock attempt should in principle be able to run the *real* `claude` CLI against the *real* fixtures and the *real* checker — the simulated-artifact boundary that limited `copilot-fluent`'s mock runs (no real M365 tenant) should mostly not apply here. But the Mock Learner Gremlin's own design principles state it does not drive real product sessions by default, and no cross-workshop run of any kind exists yet (its own Follow-Up Actions name a different workshop's first real run as the next milestone, full stop). Treat this as a testable design hypothesis for Wade In's own content-time dry runs to confirm, not a claimed advantage already in hand. The residual limit is named instead of traded away: an LLM attempt agent cannot simulate a real novice's fear, typos, or "which window am I even in" confusion — the friction findings that matter most for Module 01 specifically. Which is why:
3. **At least one real human terminal-first-timer pilots the arc before public launch.** A stated intent, not yet evidenced, and the only mechanism that can validate Module 01 at all. No learner-facing claim about the on-ramp's gentleness graduates past "designed to" until this exists on the record.

coderturtle additionally dogfoods every module's own tasks during content-building by construction (the checkers can't be authored without running them) — noted as necessary-not-sufficient, since the author is the opposite of the target learner.

## 12. Blast-radius honesty section

`copilot-fluent`'s §12 was about data protection inside a closed SaaS product. **Correction (Codex critique, finding 4):** `copilot-fluent`'s own document doesn't establish a categorical "literally could not touch the learner's machine" claim — it names the product as closed SaaS with no submission/scanning tooling built yet, which is narrower. Stated accurately: a browser-mediated SaaS chat has no general shell or filesystem access to the learner's machine; Claude Code does, by design, as the whole point of the product. This workshop's honest equivalent is starker and is a first-class design layer, not a disclaimer: **a real agent with real shell and file access can delete real files.** A SaaS chat cannot `rm -rf` a learner's machine; Claude Code, pointed at the wrong directory and waved through a permission prompt, can. The design responses, each named with its limits:

- **Sandbox by default, for the entire graded arc.** Every exercise in Modules 01-08 and 10 lives inside the workshop-provided scratch directory; nothing touches the learner's real files by default. The sandbox `CLAUDE.md` states the boundary to every session (a soft control, per §8's honesty about instructions).
- **Real-file work is a taught, late-arc skill (Module 09), never an assumption.** The ritual — copy in, back up, manifest, preview, verify — is the workshop's equivalent of `copilot-fluent`'s liability guardrails: same first-class seriousness, different actual risk.
- **Permission prompts are the rail, and habituation is the named failure mode.** A learner who reaches Module 08 will have approved many actions over seven prior modules — the exact count is unmeasured and asserted here only as "many," not the "hundreds" the prior draft stated without evidence. The real risk isn't a rogue agent but a trained-to-click-yes human. Content must teach *what to read before approving*, not just that prompts exist — and Module 09's closed-set safety exercise tests exactly this. Honest limit: no checker can verify attentiveness; this lives in Tier 2 and in content design (deliberately varying what prompts ask, so blanket approval is occasionally visibly wrong).
- **Privacy: prompts and read file contents leave the machine.** **Flagged for live verification, not asserted as settled (Codex critique, flagged-for-verification 4):** exactly what leaves the machine, what's retained, and under what policy varies by plan, tool behavior, and account type — the specific claims here must be re-checked against Anthropic's current documentation before reaching learner-facing copy, same as every other live-product claim in this section. Fixtures are fictional precisely so nothing sensitive needs to enter the sandbox regardless of the exact data-handling answer; the distribution-warning analog to `copilot-fluent`'s: learners are told plainly not to put confidential employer data into workshop exercises, and Module 09 makes data-sensitivity part of the real-folder ritual ("what would you never point it at").
- **Nondeterminism honesty:** the checker is deterministic; the agent is not. A learner can direct correctly and still need a retry when a session takes a wrong path — content must frame retries as normal verification-loop behavior, not learner failure, or the deterministic gate reads as punitive to exactly the audience it's meant to reassure.
- **Open verification task:** the claims above about Claude Code's own permission model and data handling were drafted from general product knowledge, not re-fetched from Anthropic's live documentation in this pass. Re-verify before any of it reaches learner-facing copy — the same rule `copilot-fluent` §12 applied to its Purview claims.
