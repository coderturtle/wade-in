## 1. The one-line problem

Claude Code is a capable general-purpose work tool that most non-technical knowledge workers will likely never open, because it lives behind a surface — the terminal — that they have never used and that most existing tutorials assume they have. (This is this document's own impression, not a verified survey — see §9.) This workshop's bet: a learner who has literally never opened a terminal can, through one gated, continuously-scenarioed arc, become someone who launches Claude Code themselves and does real research, document, spreadsheet-adjacent, and light-automation work with it — gated by a genuinely deterministic checker script at every module, a stronger gate than this factory's prior non-engineering-audience workshop had (§8).

## 2. Audience

Non-technical knowledge workers — the same audience shape as `copilot-fluent` (no git, no CLI, no coding-agent background), with an explicitly **harder floor: zero prior terminal experience**. The design assumption is a learner who has never opened a terminal, does not know what a prompt or cursor is, and has never typed `cd` or `ls`. This matters structurally, not just tonally: `copilot-fluent`'s learner worked inside M365 apps they already trusted and used daily; this workshop has no equivalent already-trusted surface, because Claude Code's own interface *is* the subject. Module 01 exists specifically to build the floor the rest of the arc stands on (§7).

Hard prerequisites, named plainly rather than discovered mid-module:

- A computer the learner controls (can install software on): macOS 13.0+, Windows 10 1809+/Server 2019+, or a supported Linux distribution (Ubuntu 20.04+, Debian 10+, Alpine 3.19+), 4 GB+ RAM - verified live against Anthropic's current system requirements 2026-09-14 (`code.claude.com/docs/en/setup`). All three platforms are in scope from Module 01 (§11) - the module's checker contract needs a per-OS branch, not a Unix-only design.
- A Claude Pro, Max, Team, Enterprise, or Console account (the free claude.ai plan does not include Claude Code access) - verified live 2026-09-14 (`code.claude.com/docs/en/authentication`).
- Willingness to run one install command (copy-paste, per-OS) and complete a one-time browser login. Module 01 owns this full sequence (§11). Nothing else is assumed.

**Solo by design — a genuine simplification over `copilot-fluent`:** no exercise in this arc requires a second person, a shared tenant, a colleague to share with, or an admin's approval. Every module runs on the learner's own machine. Every module's *starting business data* (client records, booking sheets, financial figures) is fictional and workshop-supplied; Modules 05 and 09 are named, deliberate exceptions that reach outside that fictional data — Module 05's sources are real, live, public vendor pages, and Module 09 deliberately leaves the sandbox to touch a few of the learner's own real files (or stand-ins). The only per-learner variance beyond that is their own machine and account (§11), not an organization's policy surface.

## 3. Format

Self-paced, public — the published site is the **primary learner surface**, same as `copilot-fluent`, not a maintainer build journal. Site implementation is a later-phase deliverable, not this document's.

**A real structural difference from `copilot-fluent`:** `copilot-fluent` had a two-way split — the site is where you read, your M365 apps are where you do. This workshop has a **three-way split**: the **site** carries the instructions, the scenario, and each module's gate; the **terminal** is where the doing happens; and **Claude Code's own file output** — the files the learner's session actually produces on disk — is the artifact submitted against the gate, verified by running a checker script against those real files (§8). This workshop is not the first in this factory to grade a filesystem-resident artifact (`borrow-native` already gates every module on `cargo test`/`cargo clippy`; `closed-book`/`heartbeat` use real local checkers too) — it is the first *non-engineering-audience* workshop with one, and the first workshop where "the terminal" and "the filesystem the checker inspects" are the same session a total beginner is driving for the first time.

**Distribution, given a no-git audience:** the workshop materials (fixtures, the sandboxed scratch directory, the checker scripts) ship as a downloadable archive from the site — the learner never clones anything. Exact packaging is a content-time decision; the design constraint it must satisfy is "obtainable and unpackable by someone who has never used a terminal, before Module 01 has taught them anything."

**Adopted from `copilot-fluent`: the site-publishes-module-content vocabulary-leak safeguard.** Per the Workshop Gremlin's non-engineering variant, a site that renders `modules/*/README.md` directly must render a plain, vocabulary-free placeholder for any module still carrying its "Skeleton only" banner — the module-README template's own vocabulary ("Tier 1," "Coachgremlin," "self-attested," "grading key") is maintainer-facing and unsafe to publish raw. This workshop's site inherits that safeguard as a build requirement.

**Rough total time commitment, stated for a busy-professional audience:** budget roughly 10-13 hours across ten modules, unevenly distributed — Module 01 is deliberately slow (45-60 minutes for material an engineer would skim in five), and the Module 10 capstone is clearly the longest single sitting (2-3 hours). Stated as an estimate, not a commitment: no module has authored content yet.

## 4. Subject vs. method

Named separately per the Workshop Gremlin's standing discipline, with an unusual wrinkle this factory has seen only once before (`terminal-velocity`): subject and method partially collapse into each other here. The interface being taught is also the interface the learning happens in.

**Subject:** Claude Code — the real `claude` CLI in a real terminal, no wrapper, no simplified or hidden version. The gentleness this audience needs comes from pacing and hand-holding in the content, never from hiding the real tool. In-scope capabilities, enumerated as the closed set the module arc must cover (§7 carries the coverage check):

1. File reading and editing (Claude Code reads and edits files at the learner's direction).
2. Running commands — including simple scripts Claude Code writes and runs on the learner's behalf; the learner directs and verifies, never reads or writes code by hand.
3. Web research (Claude Code's web search/fetch capabilities).
4. File-based automation and templating — batch renaming, CSV/spreadsheet-adjacent munging, templated document generation.

Plus two things this workshop owns that aren't Claude Code capabilities at all: **terminal literacy itself** (Module 01, before Claude Code enters the picture) and **the safety discipline for pointing a real agent at real files** (Module 09, taught late-arc as an explicit skill, never assumed — see §12).

**Explicitly out of scope, with the line that matters named:** git, subagents/Task delegation, MCP servers — and, most importantly, **any exercise where the learner is expected to read or write code themselves** rather than directing Claude Code to do so. The moment a module asks the learner to understand a script's contents, it has quietly become a programming workshop, which this is not. Learners direct, constrain, and verify; Claude Code implements. This is a hard design rule for every module in §7 — easy to drift across accidentally at content time (a checker verifying a script's *output* is fine; a rubric asking the learner to *explain the script* is a violation).

**Method:** a named-scenario-driven, two-tier-gated, self-paced format — the broad lineage every prior workshop in this factory shares, though not every specific property was universal from the start (`terminal-velocity` ran an all-subjective rubric with no deterministic tier). This workshop's real distinguishing property: its Tier 1 is a genuinely scriptable, deterministic checker (§8), closer to `borrow-native`'s `cargo test` tier than to `copilot-fluent`'s checklist — the first time this factory's non-engineering-audience variant has had one.

## 5. The shared scenario: The Double Deuce

**The Double Deuce** is a live-music venue and events hall in the fictional small town of Jasper, Missouri. The learner plays its newly hired **Operations Coordinator** — a deliberately cross-functional role (vendor research, event documents, booking spreadsheets, file wrangling, light automation), matching `copilot-fluent`'s own cross-functional design rather than departing from it. Every module's exercise is drawn from this one continuing workplace, per the factory's named-shared-project principle (`relay`, `Checkout`, Kellerman & Castle).

**The scenario device that generates the fixtures:** the learner's predecessor — a long-serving, recently retired operations man named **W. Garrett** — left behind years of chaotic files: inconsistently named photos, half-corrected phone lists, unreconciled booking sheets, and a handwritten-feeling operations handbook. Inheriting and gradually taming Garrett's files *is* the arc's continuing thread, and the learner's own growing `my-pack/` (§7, Module 10) is framed in-scenario as writing the handbook's replacement.

**Naming, recorded as settled decisions:**

- **The workshop name, Wade In, is settled** — chosen by the human from 8 candidates during the naming pass. Rationale: it plays two ways at once. To the learner it is the literal promise — ease in gently, ankle-deep first. Inside the factory's established Patrick-Swayze-movie-universe in-joke pattern, it is a *Road House* callback: Wade Garrett, the veteran mentor. Same discipline as Kellerman & Castle: the reference plays completely straight during all graded content and is revealed once, deliberately, after the capstone.
- **The org and cast are this document's own decision**, made the way `copilot-fluent`'s §5 made its firm a real decision: the Double Deuce is the *Road House* venue itself, and the predecessor whose files the learner inherits is Wade Garrett — which is also why the workshop is named what it is, a fact the learner only learns at the reveal. The cast is drawn from the same Swayze-verse but deliberately does **not** reuse Kellerman & Castle's cast; the two workshops share a universe, not a payroll. No gate ever keys on a character's identity, same as `copilot-fluent`.

1. ## 6. Curriculum anchor: none external, and why

**There is no external certification anchor for this workshop, on purpose.** Unlike AB-730 for `copilot-fluent` or Ardan Labs for `borrow-native`, no known real, current, published certification or blueprint exists for "using an agentic coding CLI as a non-engineer." This document does not invent one, imply equivalence to one, or stretch an adjacent one to fit. If a future pass is tempted to name an external credential this workshop "maps to," that temptation is the signal to verify live that such a credential exists and actually fits.

**Internal awareness note, not a learner-facing claim:** Anthropic's own Claude Certification program — specifically the **Claude Certified Architect** track that `closed-book` anchors to — exists and is real, with an agent-literate-practitioner audience, characterized by the human as "more engineer focused" than Wade In's zero-terminal-experience audience. Where mechanics genuinely overlap (how to write an effective prompt; how to verify AI output), `closed-book`'s already-authored content may be reusable raw material at content time. This is a maintainer-side reuse note only; no learner-facing copy may present Claude Certification as this workshop's target, stepping stone, or equivalent.

**Success is defined entirely internally**, by this workshop's own module arc and gate design: a learner who has passed every gate can open a terminal, launch Claude Code, and do real research/document/spreadsheet-adjacent/automation work. The precise claim is about skills, not a guaranteed real-file demonstration: the capstone (Module 10) is sandboxed against a supplied fixture packet, and Module 09's real-folder exercise permits stand-ins, so a completer may never have touched personal files during the workshop itself — what the arc evidences is that Module 09 teaches and checker-verifies the *ritual* for doing real-file work safely, and what travels with the learner afterward is the takeaway pack (§7). The honesty cost of having no external anchor: there is no third-party bar to dogfood against, so this workshop's validation burden falls entirely on §10's mechanisms, and its coverage claims (§7) are self-referential — checked by enumeration against §4's own in-scope list, which this document controls. That is a weaker external position than `copilot-fluent` had, named as such.

## 7. The module arc

**Arc shape:** nine modules plus a synthesis capstone (ten total). The sequencing logic is a dependency ramp: Module 01 teaches the terminal and installs the `claude` CLI (though the learner's first real *session* is Module 02); nothing runs a Claude-authored script before Module 04; the middle modules (05-08) each exercise the in-scope capabilities, though not with perfectly even one-capability-per-module granularity — Module 06 re-exercises Module 03's file/document work against a new artifact shape, and Modules 07-08 both exercise automation/templating; nothing touches the learner's real files until safety is taught as its own module (09); and the capstone (10) combines everything against new fixture data. The prerequisite graph itself is acyclic and every module's prerequisite is strictly earlier (02→01, 03→02, 04→03, 05→02, 06→03, 07→04, 08→04/07, 09→03/04, 10→01-09).

**Coverage check by direct enumeration** (per §4's closed in-scope list): capability 1, file read/edit — checker-gated in Modules 03 and 06. Capability 2, running commands/Claude-authored scripts — checker-gated in Modules 04 and 08. Capability 3, web research — exercised in Module 05, with the arc's weakest deterministic tier (below). Capability 4, automation/templating — checker-gated in Modules 07 and 08. That is 4/4 in-scope capabilities each **assigned** to at least one checker-gated module — meaning assigned to an honest learner's designed-path attempt, not mechanically evidenced for every completer: Module 05's checker is `[structural-only]` (below, §8), verifying the brief's shape and sourcing discipline but not that web research actually happened or that any claim is true, and its stated fallback substitutes cached excerpts for live web access.

**Mechanical-checkability discipline, applied to every Tier-1 item below:** every Tier-1 item is a count, a checker-recomputed value, an exact string *the module gave the learner up front*, or a closed-set comparison — never a natural-language phrase the learner must happen to word right (this factory's own Mock Learner Gremlin found a fully correct submission can fail a phrase-match check purely on wording variation). Checker-recomputed ground truth beats embedded answer keys wherever the task allows — a checker that re-derives the expected total from the fixture files is testing the work, not the learner's ability to transcribe a key, and it stays correct if fixtures are revised. `[structural-only]` tags mark honesty, not failure: where a task's correctness genuinely isn't machine-checkable, the Tier-1 item checks structure only and says so, and the substance moves to Tier 2 explicitly.

## 8. The two-tier gate

**Tier 1 — a real deterministic checker script, this workshop's structural advantage.** Unlike `copilot-fluent`'s subject (a closed SaaS product whose outputs live inside apps this factory's tooling can't touch), Claude Code's own working medium is the learner's real filesystem — a shipped shell script can run real, scriptable, deterministic checks against the learner's actual produced files: recomputed totals, checksum comparisons, closed-set membership, exact specified strings. The precise distinction from `copilot-fluent`: `copilot-fluent`'s own Tier 1 was genuinely mechanically checkable too (counts, exact-string comparisons against a hidden key, closed-set answers) — it just lacked a *product-native correctness oracle*, so it needed a hidden-key grader because nothing on the learner's own machine could evaluate it. This workshop's checker is **locally executable** by the learner's own harness, so it can be run, iterated against, and re-verified before submission — genuinely closer to `borrow-native`'s `cargo test` tier than to `copilot-fluent`'s checklist-plus-hidden-key. The learner runs the checker either directly (Module 01 taught them how) or by asking Claude Code to run it; either way the only passing signal is the checker's own printed `RESULT: PASS (n/n)` line with the full pass count.

**The known trap.** `closed-book`'s own multi-cycle checker-hardening history surfaced three real bypass patterns (a checker-execution bypass via cwd-swap/exit-code tricks; a test-fixture confound where correlated inputs mask what a check actually inspects; a prose-checker negation-exclusion bypass) — documented in this factory's memory system and in the Workshop Gremlin's own Follow-Up Actions, though as an unchecked item there, not yet promoted to that file's standing guidance. Wade In treats them as load-bearing anyway. Its checkers are built hardened **from the start, not retrofitted**: each check resolves the workshop root from its own script's real, symlink-resolved path (never trusting `cwd`, and resolved physically since even `/tmp` is itself a symlink on macOS — a distinction that produced a real false-fail bug on Module 01's first cross-model review pass until fixed); verifies fixture integrity by an embedded checksum pinned in the script itself, not a copy taken from the live fixture at evaluation time (**correction, 2026-09-14: an earlier version of this paragraph, and Module 01's own first-drafted checker, both described copying fixtures into a neutral temp directory before comparison — neither actually did; the temp directory existed but was unused for that purpose. The embedded-checksum approach is the real, verified defense; this paragraph is fixed to describe what the code actually does, not what an earlier design draft assumed it would need to do**), so an agent that "fixes" the inputs to match a wrong output still fails, not passes; recomputes ground truth from those pristine values where a module's check needs to derive one; rejects a symlink or a hard link standing in for a required file (both demonstrated as real bypasses on Module 01, not hypothetical ones); and prints an explicit pass-count-verified result line with nonzero exit on any failure. §7's own design rule (no natural-language phrase checks) avoids the prose-checker bypass by construction. A learner's agent could stumble into the cwd/exit-code pattern by accident, with no intent to game — which is why this is built in from day one rather than treated as an adversarial edge case.

**A named limit `copilot-fluent` never had to face: the checker ships to the learner.** These are local scripts inside the downloaded workshop folder — inspectable by a curious learner, and more realistically by the learner's own Claude Code session if asked (or if it wanders). A check whose expected values are recomputed from fixtures forces real work regardless (satisfying it *is* doing the task, §7's design preference); but closed-set keys (Module 09's safety-exercise answers) are readable by anyone who opens the script. The mitigations are honest but soft: a `CLAUDE.md` instructs sessions never to read or modify `checks/`, and the site tells learners the checker is the referee, not the study guide — and per the Mock Learner Gremlin's own Design Principle 1, **an instruction is not a control**. Tier 1 establishes that the artifact has the required properties; it cannot establish provenance (that Claude Code, directed by this learner, produced it) and cannot stop a determined self-cheater. Both are inherent limits of self-paced local grading, carried as named limits, not solved problems. **Open design question (§14): is the safety-instructing `CLAUDE.md` the same file as Module 03's learner-editable `wade-in-workshop/CLAUDE.md`, or a separate, non-learner-editable file?** Not yet specified. Also note plainly: as of this design doc's own drafting, the live repo had no checker, no modules, no site, and no `CLAUDE.md` of either kind yet — every present-tense statement in this section describes an intended mitigation, not one that was already built when this section was written. (Status update, later same day: the module skeleton and site now exist — see `docs/decisions.md` — but still no real checker script or `CLAUDE.md`; that remains content-authoring-time work.)

**Tier 2 — an AI-graded conceptual rubric, with a real but partial improvement on `copilot-fluent`'s Tier 2.** `copilot-fluent`'s Tier 2 had the product being taught grade its own output — a named, untested circularity, criticized for using "the same probabilistic product," with no pinned model, no repeatability guarantee, and no disagreement path. Here the conceptual tier follows every *prior* workshop's shape instead: **Coachgremlin grades it** — a separate, fresh-context invocation against the learner's artifact plus a supplied rubric, not the closed product judging work it produced inside itself. Claude Code isn't the closed product being taught the way M365 Copilot was: it's an open harness, and the grading prompt is portable. But this document does not actually answer `copilot-fluent`'s three specific criticisms — no model is pinned, no repeatability guarantee is stated, no disagreement path is defined (§14 covers this). A self-paced learner's fresh-context grader will, in practice, usually still be a Claude model; fresh context and a portable rubric reduce coupling to the exact product-under-test, they do not eliminate same-model-family circularity. What genuinely differs from `copilot-fluent`: Tier 2 is never the sole arbiter of mechanical correctness here, because Tier 1 genuinely is deterministic — a real, narrower advantage, not a full escape from the circularity. An AI grading AI-assisted work also remains an instance of the over-reliance this workshop teaches learners to watch for — Modules 02 and 09 should name that parallel in content. Per the Mock Learner Gremlin's Design Principle 9, a clean AI self-check is weak evidence against **value-judgment-shaped** failures specifically — Wade In's Tier-2 rubrics are mostly judgment-shaped by construction, so content-time validation must include independent-verification passes, not self-check-only runs. Grading-prompt injection is a smaller surface here than `copilot-fluent`'s injection-teaching module, but the delimiter-and-treat-as-data discipline is carried forward as a content-time acceptance criterion anyway.

## 9. Differentiator vs. existing material

**Verification status, updated 2026-09-14 at content-authoring time: verified live against Anthropic's own current documentation (`code.claude.com/docs/en/terminal-guide`, `.../setup`, `.../authentication`).** The prior draft's claim in this section ("Anthropic's docs... don't teach the terminal itself") was **false, caught by live verification rather than assumed correct** — the same discipline this factory has learned to apply to every claim about a live product or a competitor's material, most recently `copilot-fluent`'s own AB-730/Microsoft-material correction.

- **Anthropic publishes a real, current "Terminal guide for new users"** (`/docs/en/terminal-guide`) covering exactly this audience: opening a terminal for the first time (with platform-specific instructions — Spotlight on macOS, the app menu on Linux, `Win+X` on Windows), installing Claude Code, completing first login, and a first interaction, for **macOS, Linux, and Windows alike**, each with a real troubleshooting section. This is a genuine, current, zero-experience-assumed on-ramp this workshop cannot claim doesn't exist. **What it does not do, verified by reading it in full**: it does not teach general terminal navigation (`cd`, creating/copying files and folders, what a "current directory" is) beyond the one install-and-launch sequence — a learner who follows it can start Claude Code but hasn't been taught to navigate a filesystem, recover from a stuck terminal, or do anything terminal-native beyond that single scripted path. It is also an ungraded walkthrough with no exercise, no retained-skill check, and no takeaway beyond "Claude Code is now running." Wade In's actual differentiation from this real prior art: broader terminal literacy (navigation, file operations, recovery — not just install-and-launch), a gated checker-verified exercise per module, one continuing scenario, and a keepable takeaway pack. Named honestly as narrower and more specific than the prior draft's blanket claim.
- Anthropic's other official Claude Code documentation and quickstarts (beyond the terminal guide specifically) do generally assume a reader already comfortable in a terminal. They are reference material, not a gated curriculum. This workshop stands alongside them (they remain the product's source of truth) and below them (starting a full floor earlier, with a check that skills were retained).
- **Terminal-literacy primers for beginners** exist in quantity, but teach the terminal as an end or as a programming on-ramp — none known to this draft teach it as a short ramp into agentic non-programming work with a gate.
- **The general "AI for knowledge workers" genre**, including `copilot-fluent`'s own subject area. The real distinction from that genre is **arbitrary local filesystem/shell access versus application- and tenant-mediated file grounding** — `copilot-fluent`'s learner works with files *through* Word/Excel/PowerPoint, inside whatever a tenant admin has exposed (M365 Copilot requires file-grounding access as a hard prerequisite); this workshop's learner works on files directly, through a shell, with no application or tenant boundary in between.

What differentiates this workshop, each claim qualified as a design intent, not an evidenced advantage per §10: **gated, deterministically** — a stronger gate tier than any non-engineering material this factory has built before, including `copilot-fluent`'s own checklist tier; **a genuinely zero-floor on-ramp** that owns terminal literacy rather than outsourcing it; **one continuing scenario** with a keepable, personal takeaway pack; **a taught safety discipline** for real-file work (§12) that ad-hoc tutorials typically skip.

## 10. External validation / dogfooding

With no external certification to sit (§6), this workshop's validation is built from three mechanisms, each a stated commitment rather than existing evidence:

1. **Adversarial checker dry runs, from the first checker built.** Every module's checker gets a `borrow-native`-style good/naive pair before the module ships: a correct attempt must pass with the full count, and at least one scripted-flaw attempt must fail — plus the §8 bypass patterns each demonstrated to fail loudly.
2. **Mock Learner Gremlin per module** (per Coachgremlin's Workflow step 8), with personas rebuilt for this audience — a genuinely zero-terminal-experience persona, not `copilot-fluent`'s office-worker persona reused. **A hypothesized fidelity advantage, not yet a proven one:** because this subject's surface is itself scriptable, a mock attempt should in principle be able to run the real `claude` CLI against the real fixtures and the real checker, unlike `copilot-fluent`'s mock runs (no real M365 tenant). But the Mock Learner Gremlin's own design principles state it does not drive real product sessions by default, and no cross-workshop run exists yet — treat this as a testable hypothesis for Wade In's own content-time dry runs, not an advantage already in hand. The residual limit either way: an LLM attempt agent cannot simulate a real novice's fear, typos, or "which window am I even in" confusion — the friction findings that matter most for Module 01 specifically.
3. **At least one real human terminal-first-timer pilots the arc before public launch.** A stated intent, not yet evidenced, and the only mechanism that can validate Module 01 at all.

## 12. Blast-radius honesty section

`copilot-fluent`'s §12 was about data protection inside a closed SaaS product with no general shell or filesystem access to the learner's machine. Claude Code has that access by design, as the whole point of the product. This workshop's honest equivalent is starker and is a first-class design layer, not a disclaimer: **a real agent with real shell and file access can delete real files.** A SaaS chat cannot `rm -rf` a learner's machine; Claude Code, pointed at the wrong directory and waved through a permission prompt, can. The design responses, each named with its limits:

- **Sandbox by default, for the entire graded arc.** Every exercise in Modules 01-08 and 10 lives inside the workshop-provided scratch directory; nothing touches the learner's real files by default. This is currently enforced entirely by instruction (a `CLAUDE.md` stating the boundary) — a soft control, per §8's honesty about instructions applying here too. **Open question for content time (§14): should this also be enforced technically, via Claude Code's own permission-mode/allowed-directory settings, rather than relying on instruction alone?** Not yet designed.
- **Real-file work is a taught, late-arc skill (Module 09), never an assumption.** The ritual — copy in, back up, manifest, preview, verify — is the workshop's equivalent of `copilot-fluent`'s liability guardrails: same first-class seriousness, different actual risk. A specific privacy note is due here that the current draft under-states: Module 09 is the one module where a session reads real personal file content, and whatever data-handling policy applies (below) applies most concretely at exactly that moment — content time should say so explicitly at the point the learner opts into real files, not only in this general section.
- **Permission prompts are the rail, and habituation is the named failure mode — arriving too late in the current design.** A learner who reaches Module 08 will have approved many actions over seven prior modules (the exact count is unmeasured); the real risk isn't a rogue agent but a trained-to-click-yes human. Module 09's closed-set safety exercise tests *recognition* of unsafe asks, not demonstrated in-the-moment behavior — a real, named gap between what a PASS proves and "this learner reads prompts carefully." Content time should interleave at least one moment earlier than Module 09 where blanket-approving a prompt visibly produces a wrong or undesirable result, rather than concentrating the entire safety-habit lesson at the end of the arc.
- **Privacy: prompts and read file contents leave the machine — flagged for live verification, not asserted as settled.** Exactly what leaves the machine, what's retained, and under what policy varies by plan, tool behavior, and account type; re-check against Anthropic's current documentation before this reaches learner-facing copy. Fixtures are fictional precisely so nothing sensitive needs to enter the sandbox regardless of the exact data-handling answer, for every module except Module 09 (above). Learners are told plainly not to put confidential employer data into workshop exercises, and Module 09 makes data-sensitivity part of the real-folder ritual.
- **Nondeterminism honesty:** the checker is deterministic; the agent is not. A learner can direct correctly and still need a retry when a session takes a wrong path — content must frame retries as normal verification-loop behavior, not learner failure, or the deterministic gate reads as punitive to exactly the audience it's meant to reassure.
- **Open verification task:** the claims above about Claude Code's own permission model and data handling were drafted from general product knowledge, not re-fetched from Anthropic's live documentation. Re-verify before any of it reaches learner-facing copy.
